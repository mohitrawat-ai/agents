Customer onboarding · AWS access

Grant Ingren read-only access to your AWS account

Ingren's RCA agent investigates incidents by reading your AWS telemetry: metrics, logs, and resource configuration. To do that it assumes an IAM role in your account. You create the role once, in the AWS console. This page walks through the four steps.

Read-only. No permission in this setup can create, modify, or delete anything in your account.

Step 1 · IAM → Policies → Create policy → JSON

Create the describe policy

Name it ingren-rca-describe. It covers the resource-inspection calls that the AWS managed read-only policies in step 3 don't. Paste this JSON in the policy editor's JSON tab.

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "RcaResourceDescribe",
            "Effect": "Allow",
            "Action": [
                "ec2:Describe*",
                "rds:Describe*",
                "rds:ListTagsForResource",
                "dms:Describe*",
                "elasticloadbalancing:Describe*",
                "autoscaling:Describe*",
                "sqs:ListQueues",
                "sqs:GetQueueAttributes"
            ],
            "Resource": "*"
        }
    ]
}
Describe and List actions only Name: ingren-rca-describe

Step 2 · IAM → Roles → Create role

Create the role Ingren will assume

Name it ingren-rca-readonly. In the wizard, pick trusted entity type AWS account → Another AWS account, enter account ID 537124933640, and tick "Require external ID". Paste your external ID value. The wizard produces exactly this trust policy:

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "sts:AssumeRole",
            "Principal": {
                "AWS": "arn:aws:iam::537124933640:root"
            },
            "Condition": {
                "StringEquals": { "sts:ExternalId": "<EXTERNAL_ID>" }
            }
        }
    ]
}
Why the external ID matters. The trust policy alone says "Ingren's account may assume this role". The external ID condition adds "…and only when it presents your secret". Together they prevent the confused-deputy problem. Keep the value private.

Attach these 4 policies to the role

Three are AWS managed. The fourth is the one you created in step 1.

Step 4 · Done — share the ARN

Send us the role ARN

Open the role and copy its ARN from the summary panel. It looks like this:

arn:aws:iam::<YOUR_ACCOUNT_ID>:role/ingren-rca-readonly

Reply with the ARN on the same channel where you received your external ID. We confirm access with a read-only test call and tell you when the RCA agent is live.

Optional add-on

Deeper-logs add-on: CloudTrail, RDS log files, ALB access logs

Some investigations need three more read paths: CloudTrail event history (who changed what, and when), RDS log file download (database error and slow-query logs), and ALB access logs in S3 (per-request traffic during an incident). To enable it, use this JSON for ingren-rca-describe in step 1 instead of the base version — everything else stays the same.

{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "RcaResourceDescribe",
            "Effect": "Allow",
            "Action": [
                "ec2:Describe*",
                "rds:Describe*",
                "rds:ListTagsForResource",
                "rds:DownloadDBLogFilePortion",
                "dms:Describe*",
                "elasticloadbalancing:Describe*",
                "autoscaling:Describe*",
                "sqs:ListQueues",
                "sqs:GetQueueAttributes",
                "cloudtrail:LookupEvents"
            ],
            "Resource": "*"
        },
        {
            "Sid": "RcaAlbAccessLogs",
            "Effect": "Allow",
            "Action": ["s3:ListBucket", "s3:GetObject"],
            "Resource": [
                "arn:aws:s3:::<ALB_LOGS_BUCKET>",
                "arn:aws:s3:::<ALB_LOGS_BUCKET>/*"
            ]
        }
    ]
}
<ALB_LOGS_BUCKET> is the S3 bucket where your load balancer writes access logs. Find it under EC2 → Load Balancers → your ALB → Attributes → Access logs. The S3 grant is scoped to that one bucket. Every added action is still read-only.
Adds 3 read paths — still zero write permissions Replaces the step 1 JSON, not the role

This is a typical permission request. The exact actions can change based on your architecture. The structure stays the same: an IAM role in your account, an external ID, and read-only policies.
